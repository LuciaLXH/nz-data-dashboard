## 二、审查过程复盘（Xiaohan 的问题与思考）

> 每一条 = 当时的问题 → 核心思考 → 沉淀的技能。这些是讲解项目时的"我的审查方法"素材。

### 1. "我怎么知道你给我的是对的数字？"
- **思考**：不能靠信任叙述，要能**溯源到官方源头**。
- **验证**：Stats NZ 官方探索器（浏览器可点）复核 Auckland 2025 = 1,816,000；再用"相关数字交叉印证"——官方发布页写 Auckland 年增 2.5%，我们算出 2.46% ≈ 吻合。
- **沉淀的方法（三步配方）**：① 溯源（数字来自哪个原始文件/API，不是我手打的）② 复查官方（同一官方源再查一次）③ 交叉印证（相关数字自洽）。
- **讲解价值**：面试可讲"我没有盲信任何数值，抽样对官方源头独立复核"。

### 2. "覆盖率代表什么？和城市化/产业结构有关吗？有没有官方定义？"
- **思考**：一个新指标出现时，先问**它定义了什么、不定义什么**，再问**它与现实世界现象的关系**。
- **结论**：覆盖率 = 纳入统计的供水服务人口 ÷ 区域常住人口。它不是服务质量指标，是"数据视野标尺"。与城市化强相关（有官方锚点：Taumata Arowai NEPR 报告 p.13 —— 全国 84% 人口接公共管网，其余为自供水/农村）。产业结构的影响是间接的（农业区人口分散、工业用水不进人口口径）。
- **讲解价值**："我学会了区分『指标含义』与『现实关联』，并用官方报告原话（84%）支撑判断"。

### 3. "Waikato 覆盖仅 36%：是数据源不完整还是抓取出了问题？"
- **思考**：遇到异常数字先区分三类原因——**源数据缺失 / 管线 bug / 分析范围选择**，不要急着下结论。
- **验证**：从原始 NEPR CSV 证实源数据完整（全 NZ 556 个系统，Waikato 区/ Taupō/ South Waikato 等都在）→ 结论是 W1 阶段"每区只精选主城供应商"的范围选择。
- **修复**：把分析升级为**全量 269 个系统**，覆盖 68–96%；Otago/Southland 画像因此显著修正（QLDC 旅游区拉高人均）。
- **讲解价值**：这是一个完整的"发现问题 → 定位根因 → 修复 → 结论改变"案例，且证明**原始数据落盘**的价值（任何汇总都能重算）。

### 4. "你参考什么官方文件做的区域映射？"
- **思考**：数据来源的出处（provenance）要经得起追问；被问到时要诚实说清"知识 vs 文件"。
- **验证**：映射最初基于我的地方政府地理知识（会话中未查特定文件）→ 用官方人口数据做**数值验证**：每大区的 TA 级人口求和必须等于 RC 级人口。结果 Auckland/Hawke's Bay/Southland 精确为 0，其余 3 区差 0.3–0.7%——用数据定位出这是 Stats NZ 著名的"跨区域辖区"效应（Taupō ~3,850 人归 BOP、Waitaki ~1,900 人归 Canterbury），**非映射错误**。
- **讲解价值**："我主动坦白映射的知识来源，然后用官方数据证明了它的正确性"——诚实 + 可验证，是最好的防御。

### 5. "改前端会更难吗？后端数据和前端是不是互相独立？"
- **思考**：架构理解——数据管线与展示层解耦，改一端不动另一端。
- **结论**：项目评审时已定"静态站只读 `data/processed/*.json` + JSON Schema 契约"，因此独立成立。但仍建议**先审数据再等可视化**：W2 分析建在 W1 数据上，数据错会导致分析重做，成本更高。
- **讲解价值**：能讲清"为什么这个架构决策让项目可维护"。

### 6. "我能在自己电脑跑吗？怎么验证我没跑错？"
- **思考**：可复现性 = 最大信任背书；环境细节（如 `.env` 加载、前台进程占用终端）都是坑。
- **验证**：用户亲手跑 `make data`，`_runs.jsonl` 多出一行与 AI 运行完全一致的 8/8 记录。
- **讲解价值**："我自己复现了整个管线，输出与预期逐项一致"。

### 7. "我把 _runs.jsonl 改名了，有影响吗？"
- **思考**：**文件名是代码的一部分**——脚本按精确路径找文件，改错名 = 程序静默新建空文件、旧历史被孤立。
- **教训**：重命名项目内文件前先问"有没有代码引用它"。
- **讲解价值**：体现对管线机械细节的理解（小而真实）。

### 8. "本地网页能给其他人看吗？"
- **思考**：区分本地预览 / 临时隧道 / 长期部署三种分享模式。
- **结论**：GitHub Pages 是正解（W3 转公开 + 开 Pages），CI 自动跑 `make data` → 部署，key 只存在于 secret。
- **讲解价值**：理解"数据刷新 + 部署"的全链路，以及公开数据项目的分享/安全设计。

### 9. "第一次做数据项目，怎么保证你的工作质量？要不要另一个 AI 监督？"
- **思考**：审查不是信任叙述，是**验证可复现性**；另一个 AI 只能做独立抽查，不能替代自己理解；最可靠的"看门狗"是 CI（定时自动复现）。
- **沉淀**：分层审查（抽查数字 → 自己跑管线 → 读代码 → git 审计）；风险分级（实时 API 数据低风险 vs 人工提取数据中风险，优先抽查后者）。
- **讲解价值**：展示"审查方法论"而不只是结果——面试加分项。

## 三、关键概念速查（讲解项目时直接可用）

| 概念 | 一句话 |
|---|---|
| 覆盖率 | 纳入统计的供水人口 ÷ 区域常住人口；衡量"数据视野"，非服务质量 |
| 全国 84% | 官方：接公共管网的人口比例（NEPR 2024/25 p.13），其余为自供水 |
| CAGR | 复合年增长率，(终值/初值)^(1/n)−1，比简单平均诚实 |
| L/人/日 口径 | 我们用的是"供应 ÷ 人口 ÷ 365"（含漏损），与"居民消费"口径不可混用 |
| CARL / ILI | 年度实际漏损（L/连接/日）；基础设施漏损指数（管网完整性） |
| 跨区域辖区效应 | Stats NZ 将个别区（Taupō/Waitaki）边缘人口统计到相邻大区，±1% 级 |
| 溯源三步 | 溯源 → 复查官方 → 交叉印证 |
| 文件名即代码 | 脚本按精确路径找文件，改名要查引用 |
| 静态站解耦 | 前端只读 processed JSON + Schema 契约，两端独立可改 |
| NEPR vs NPR | NPR 止于 2021/22；继任者 = Taumata Arowai NEPR（CC BY 3.0 NZ）|

## 四、讲解/面试要点（怎么讲这个故事）

**一句话主线**：6 个新西兰大区里，未来 5 年哪些供水区会先出现供需失衡？——增长型压力（Canterbury/Waikato）vs 效率型压力（Hawke's Bay 人均全国最高 610 L/日、Southland ILI 7.25）。

**我的审查与工程贡献（可讲的 3 件事）**：
1. **独立验证**：抽样数字对官方源头复核 + 相关数字交叉印证（如 Auckland 2.46% ≈ 官方 2.5%）。
2. **发现并修复数据盲区**：需求侧最初只覆盖主城供应商（Waikato 仅 36%）→ 升级为全量 269 个系统（68–96%），Otago/Southland 画像被实质修正——证明原始数据落盘 + 可重算的价值。
3. **映射可信度**：承认映射源于领域知识，再用官方人口数据数值验证（TA 求和 = RC），并解释残差为官方统计效应。

**诚实边界（必讲）**：L/人/日 口径（供应 vs 消费）、覆盖率 <100% 的结构性原因、计量 % 不在 NEPR 单位数据中（精选版仅供参考）、跨区域辖区 ±1% 效应。
