## 两个文件夹的职责

`nz-data-dashboard` 是实际 Git 仓库，包含 Python 抓取、DuckDB SQL、JSON Schema、测试、静态网页和 GitHub Actions。`nz-water-review` 只有早期 HTML 评审与 README 草稿，没有独立程序或 Git 仓库。两个文件与主项目 `docs/review/` 下副本逐字节相同。

早期评审中的 USER/REPO、Feng Jiang、Distinction 等是模板内容，不能复制进成品作为真实履历。其“没有 SQL”“尚未上线”等意见反映当时状态：现有项目已经提供 SQL、公开网站、许可说明和离线测试。原始评审材料保留，新增审查以本文为准。

## 恢复操作

先保存原始日志和检查最近十次运行，确认前九次成功；再按 [GitHub 重跑说明](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)执行：

```bash
gh run rerun 37996530712 --repo LuciaLXH/nz-data-dashboard --failed
```

attempt 2 使用原始提交。重跑的数据校验仍为 14/14，pytest 24 passed，但部署遇到同 run 内两个 `github-pages` 产物的冲突而失败；缓存保存也出现 warning，因为旧 key 不含 attempt。日志见 [rerun-attempt-2.log](incidents/2026-10-10/rerun-attempt-2.log)。这次错误不同于原始 HTTP 502，说明只重跑旧单 job 配置不足以恢复。

随后执行 `gh workflow run refresh.yml --repo LuciaLXH/nz-data-dashboard --ref main`，创建全新 [恢复运行 38009523209](https://github.com/LuciaLXH/nz-data-dashboard/actions/runs/38009523209)，避免同 run 的产物重名。

旧版单 job 结构会重新抓取、验证、构建和部署，而不是只重试最后一步。它验证的是原始部署故障的恢复，不是本次新增代码。

本地仓库原 HEAD 为 `45668d3`，远端比本地多一个 10 月 1 日 keepalive 空提交。执行 `git fetch origin` 和 `git merge --ff-only origin/main` 后同步到 `39b0b18`；没有覆盖用户文件。原来未跟踪的 `.agents/.xdgcache/` 是 gh 日志缓存，已加入忽略规则。

## 分析口径和后续优先级

### 优先核对需求与漏损的外推假设

`sql/02` 的 daily_demand_m3 用整个大区 ERP 乘管网人均供应量，leak_m3_day 再乘人口加权的漏损率。未接统计管网的人口也被纳入，漏损率采用人口权重而非供水量权重。因此它们是区域情景估算，不能称为管网实测总量。

以本地原始 NEPR CSV、现有 org mapping 和 supply 去重规则汇总：

| 口径 | 日供应 m³ | 日漏损 m³ |
| --- | ---: | ---: |
| 已报告年度量相加再除 365 | 1,178,309 | 264,779 |
| 现有 regional ERP 外推 | 1,326,635 | 298,671 |

已在网页、README 和 ANALYSIS 中写明估算口径，未改变现有 SQL 或图表数值。汇总证据见 [metric-audit.json](incidents/2026-10-10/metric-audit.json)。直接汇总值也只是已报告数据，仍需检查各指标的缺失和覆盖，不是独立核实的完整地区真值。

下一轮应同时输出 observed_network_supply、reported_loss 和 regional_scenario，核对 missing coverage，并以总漏损量/总供水量计算汇总漏损率。Hawke's Bay 的效率节约使用 pop_served，但“6 区需求增长”用全区 ERP，62% 比较的分母和分子覆盖范围不同，应统一后再强化结论。

“效率最便宜”“先修管再建厂”和“买到 1.5–2 年缓冲”没有成本、可回收漏损或施工可行性证据，应作为待检验规划假设。静态图里的表述也需要随下一轮分析统一重制。

### 统一年度与预测标签

`sql/02` 自动取最新人口年，但列名 pop_2025、网页 ERP 2025/2030 和文档保持固定。新数据发布时可能实际预测 2031，却仍显示 2030。新增年度测试消除了固定行数问题，但这个语义问题仍需添加 base_year 和 projection_year、同步 Schema、前端与图稿。

### 补齐季节窗口和抓取边界

`sql/03` 的 dayofyear 距离没有按年周期环绕，因此 1 月初不能正确纳入前一年 12 月末；闰日附近也可能偏一日。建议固定到闰年季节历、计算环形距离，补跨年/闰日测试后修改。Hilltop 年块结束值只写日期，对边界当天是否完整包含需要用服务器协议或原始响应核实；抓取“今天”使用 UTC 日期，而源说明采用 NZ 本地时间，须统一源时区和完整日处理。

当前每 6 小时重复拉多年 HBRC 和 ORC 历史，网络请求较多。下一步改为增量抓取实时站、缓存不变的 ORC 历史，人口有有效缓存时按月检查。45 分钟 job timeout 用于限制卡住的运行，不是减少请求量的替代方案。

### 数据健康应展示来源时间

`processed_utc` 是转换时间；不能代表 NEPR/LAWA 原始数据更新。已将网站 Findings/Charts 的 As of 标签改为 built，注明 NEPR 2024/25 或 ERP 2025；Flow 改为 Processed 并提示查看观测日期。下一步分别显示数据年度、抓取时间、最新观测日期和构建时间。31 天的 pipeline paused 阈值对 6 小时任务较宽松，应明确 stale SLA。

运行历史缓存只积累验证记录，部署失败和抓取提前终止不会出现在已发布页面的条中；部署状态应查看 Actions。缓存清理后历史也会重置。

### 文档和复现范围

保留历史评审，但添加状态索引，避免旧 README 模板和 REVIEW-JOURNEY 的旧“私有、待上线”状态误导读者。`data/raw/sample/` 当前只有 .gitkeep：干净 clone 的离线测试会跳过部分数据检查，不等于完整构建。可添加小型公开源 fixtures 与离线构建目标。

章节 B 尚未实施，应保留 pending；不要写成已证明的人口或土地利用因果结论。NEPR/LAWA 快照更新仍需要手工维护来源清单与日期。

### Actions 运行环境维护

原始日志提示部分 actions 的 Node 20 已弃用并被 runner 强制切到 Node 24；恢复运行还提示 ubuntu-latest 将迁移。后续应逐个核对官方发布说明后更新 action 版本，并在 Linux CI 验证兼容性。当前 502 与产物重名均有独立错误证据，不应把版本警告当成已确认根因。
