Q1

整体缺陷与工期

P0 核心命题的因果性站不住

「How is population growth shaping water resources across Aotearoa's regions?」这句话在 NZ 语境里有个硬伤：NZ 河流水质的主导驱动是土地利用（乳业强度、氮沥滤、河岸带），不是城市人口。你用 16 个 region 做人口增速 vs 硝酸盐/浊度的散点图 + 趋势线，会踩三个坑：

  • 生态谬误 —— region 层面的相关 ≠ 个体/流域层面的机制
  • n = 16 —— 任何相关系数都不稳健，一个 Auckland 或 Canterbury 就能翻转结论
  • 混杂 —— Canterbury 人口增长快且灌溉农业密集；Auckland 人口增长快但供水来自水库。同一个 x 对应完全不同的机制

在 ECan、Waikato RC、Taumata Arowai 这类最可能招你的地方，这会被当场问住。

三个可辩护的重构（推荐 A + B 组合）

方案命题为什么站得住
A
主线 · 推荐		 人口增长下，各 council 供水系统的人均用水、漏损与计量覆盖差异，意味着哪里最先出现供需缺口？ 这是真实的人口—水耦合（供水本就按人算），council 层面，有明确决策用户
B
深度章节		 人口增长能解释区域水质差异吗？—— 控制土地利用后并不能 把混杂本身做成发现。展示 partial correlation / 分层，统计成熟度信号极强
C
保底		 纯描述性 + 显式声明非因果 安全，但没有区分度

A 做主线（有 so-what），B 做一节 “Why I don't claim causation”（有 rigor）。这两条加起来，比原方案多出的说服力远超多做三张图。

合规提醒

你 PHF 实习的洪水—水质—AMR 分析，不要把数据或未发表结论搬进公开 repo。但「我在 PHF 做过同类分析，这里是基于开放数据的公开版本」是很强的叙事 —— 方法可以复用，数据必须换。

Q2

数据源：三处需要修正

P0 修正 1 · LAWA 没有公开 API

LAWA 是 16 个 regional council + MfE + Cawthron + Massey 的门户，它提供的是批量下载页（CSV/XLSX），不是 API。你方案里「经 data.govt.nz 的 ArcGIS GeoService 拿 LAWA 数据」是靠不住的假设。

改法：把 LAWA 的 river quality state & trend 数据当作手动下载的年度快照放进 data/raw/（README 注明下载日期与来源），不进自动管道。它本来就是年度更新，自动化没有意义。

P0 修正 2 · 河流流量直接打 council 的 Hilltop，不要走 NIWA

多数 regional council 跑 Hilltop Server，公开、免 key、REST 风格：

curl "http://gisdata.orc.govt.nz/hilltop/Global.hts?Service=Hilltop&Request=SiteList"

支持 Service=Hilltop|WFS|SOS，Request=SiteList / MeasurementList / GetData，WFS 还能带 bbox。ORC、HBRC 都有公开端点。这是整个项目里最容易实现「真的会动」的部分。

NIWA 方向有机构风险

NIWA 已于 2025-07-01 与 GNS 合并为 Earth Sciences New Zealand，MetService 并入的新 PRO 约 2025-10-01 生效。品牌、URL、门户都在变动期。更关键的是 NIWA 的水文/气候数据许可通常不是 CC BY，多数带再分发限制 —— 把它存进公开 GitHub repo 有许可风险。MVP 避开 NIWA。

P1 修正 3 · 区域人口是年度的，不是季度

Stats NZ 的 subnational population estimates 是 as at 30 June，每年 10 月发布 provisional。季度只有全国口径。所以「人口每日检查去重」—— 每天去查一个一年动一次的数字 —— 在懂行的人眼里是表演性自动化，减分。

改成每月检查，页面显示 checked 2h ago · unchanged since Oct 2025，诚实反而加分。

Q4

静态站 → Streamlit「零改动」：不成立

管道确实零改动。但前端才是大头，而前端要 100% 重写。

三个隐藏成本

  1. 图表逻辑无法复用 —— ECharts(JS) 和 Plotly/Altair(Python) 之间没有共享代码。你等于把整个可视化层再做一遍，然后维护两套会漂移的 UI。
  2. Streamlit Community Cloud 会休眠（约 7 天无访问）。招聘方点开你简历上的链接，看到 “app is waking up…” 转圈 30 秒 —— 这在求职场景是实质性负面。
  3. 数据契约实际上还好 —— 如果你坚持「processed/ 是唯一真相 + JSON + schema 版本号」，这部分确实低成本。这个架构决定是对的，保留。
P0 · 一个你还没发现的硬冲突

GitHub Free 个人账号，Pages 只能从「公开」repo 发布。私有 repo 要用 Pages 需要 GitHub Pro（付费）。

你写的「repo 先私有，做完再公开」+「第一版用 GitHub Pages」是矛盾的 —— 私有期间你根本开不了 Pages。

解法（选 a）

  • (a) ✅ 私有开发，完成后转公开再开 Pages。 反正没做完也不该给人看，本地 python -m http.server 预览足够。
  • (b) 私有开发 repo + 公开一个只放构建产物的 site repo（两个仓，麻烦）
  • (c) 用 Cloudflare Pages 或 Netlify —— 免费、支持私有 repo、且不会休眠。如果你想全程私有，这是最干净的路

建议：砍掉双前端，只做静态站

理由：秒开、永不休眠、可被引用、零冷启动。而且你简历上已经有 Streamlit 工资计算器 MVP 了，不需要再证明一次同一件事。省下的一周全部投到分析深度上，边际回报高得多。

## How it works

```
Stats NZ ADE API ─┐
Water NZ NPR ─────┼─→ scripts/  ─→ DuckDB ─→ data/processed/*.json ─→ static site
Council Hilltop ──┤     (extract)   (sql/)     + schema + _runs.jsonl    (ECharts
LAWA snapshot ────┘                                                     + Leaflet)
```

- `data/processed/` is the **single source of truth** for the front end:
  versioned JSON + JSON Schema + a UTC timestamp per source.
- Refresh cadence matches each source's real cadence — see the table below.
  This is an **automated pipeline with freshness SLAs**, not a real-time feed.
- The site's **Data Health** panel reads `_runs.jsonl`: last successful run,
  row counts, null rates, schema version, last 20 runs.

## Limitations & why I don't claim causation

- **Ecological fallacy** — council-level correlation says nothing about
  catchment-level mechanism.
- **n = [N]** — no correlation across this few units is robust; one large
  council can flip the sign.
- **Confounding** — land use (dairy intensity, irrigation) drives NZ river
  water quality far more than urban population. Section [B] shows the
  population signal weakens once land use is accounted for.
- **Site selection bias** — LAWA monitoring sites are not randomly located.
- Water NZ NPR is self-reported by councils; metering coverage varies.

## Run it yourself

```bash
git clone https://github.com/USER/REPO && cd REPO
cp .env.example .env        # add your Stats NZ API key
make all                    # fetch → transform → validate → build site
make test                   # pytest: schema, units, region names, DST, nulls
python -m http.server -d site 8000
```

`data/raw/sample/` holds a trimmed fixture set so `make test` runs offline.

## Repo layout

```
scripts/    extract + orchestrate (Python)
sql/        all business logic (DuckDB)
schemas/    JSON Schema per processed dataset
site/       static front end (ECharts + Leaflet), no build step
tests/      pytest
data/
  raw/      source snapshots + sample fixtures
  processed/ single source of truth: *.json, *.schema.json, _runs.jsonl
```

## Status

Pipeline runs on GitHub Actions: flow every 6 h, water quality and population
monthly. If the badge above is red or the site header says *pipeline paused*,
the data shown is the last good snapshot — the site degrades to stale rather
than blank, by design.
